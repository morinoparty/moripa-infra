構築が完了したあとの、日常的な運用手順とトラブル対応の指針。

## SSH は wg 経由のみ

公開 SSH は bootstrap 後に閉じてあるため、通常運用では WireGuard 経由でのみ
アクセスする。

```sh
ssh moripa@gw.wg.morino.party            # ゲートウェイ(linode-gw、10.100.0.1)
ssh moripa@site1-node1.wg.morino.party   # 10.100.0.11
ssh moripa@site2-node1.wg.morino.party   # 10.100.0.21
```

名前はハブの dnsmasq が返す(`/docs/architecture/reference` の DNS 節)。
wg クライアント側で `wg.morino.party` をハブの DNS に向けていない場合は
IP を直接使う。

<Callout title="公開SSHを閉じる前の必須確認(再掲)">
  管理者マシンを `wg_extra_peers` に登録し `make gateway` を再実行済みで、
  管理者マシンの wg0 から `ssh moripa@10.100.0.1` が通ることを確認してから
  `bootstrap_ssh_cidrs` を空にして re-apply すること。閉じたあとに wg が
  壊れた場合の復旧は Linode の LISH コンソールのみ(`/docs/admin/keys`、
  `/docs/admin/terraform` 参照)。
</Callout>

## 公開ホスト名(Caddy)の追加・変更

HTTP/HTTPS の公開は Linode 上の Caddy が担う。`<app>.site<N>.dev.morino.party` /
`<app>.site<N>.private.dev.morino.party` の規約に従う名前なら Caddy 側の変更は
不要で、対象拠点に Ingress(`ingressClassName: cilium`)を置くだけでよい(`/docs/architecture/multi-site`)。

規約外の名前を足すときは `gateway/caddy/Caddyfile` を編集して `main` に push する。
ハブの `caddy-gitops.timer` が 3 分ごとに取り込み、`caddy validate` を通してから
reload する(検証に失敗したら現行設定のまま。`journalctl -u caddy-gitops` に理由が出る)。
即時反映したいときは `ssh gw.wg.morino.party sudo systemctl start caddy-gitops`。
CI でも同じバイナリで `make lint-caddy` が走るので、壊れた Caddyfile は push 前に分かる。

<Callout title="/etc/caddy/Caddyfile を直接編集しない">
  次の取り込みで `main` の内容に戻される。`make gateway` も Caddyfile には触れない
  (Ansible が書くのは `generated.caddy`(拠点別 upstream / tls / 認証の snippet)、
  `env`(Cloudflare トークン)、`www/` の同期だけ)。
</Callout>

- ノード障害時の切り替えは Caddy が自動で行う(失敗した upstream を 30秒
  外し、別ノードへ再試行)。手作業は不要
- 証明書は Let's Encrypt の **DNS-01(Cloudflare)** でワイルドカードを自動取得・
  更新する。失敗する場合は Cloudflare トークン(`auth.sops.yml`)の権限
  (Zone / DNS / Edit、morino.party)と `journalctl -u caddy` を確認する。
  DNS-01 なので A レコードや 80 番の到達性は取得に関係しない
- Caddy の状態は `ssh gw.wg.morino.party systemctl status caddy caddy-gitops.timer`
- 認証(oauth2-proxy)の設定は `/docs/admin/auth`

## L4 サービス(HAProxy)の追加・変更

HTTP 以外のサービス(将来の Minecraft など)は Linode 上の HAProxy が受ける。当面 `tcp_routes` は空。
`ansible/group_vars/all/network.yml` の `tcp_routes` に行を足して
`make gateway` を実行する(`haproxy -c` で検証後に reload)。ノード障害時の
切り替えは HAProxy の TCP ヘルスチェックが自動で行い、手作業は不要。

- 新しい port を足したら `terraform` の `public_tcp_ports` にも追加して
  `make tf-apply`(Cloud Firewall)
- `allowed_sources` で送信元を絞る。Minecraft(Velocity 配下、online-mode=false)なら
  Velocity の IP を入れる。空だとバックエンドに誰でも直接つなげる状態になり、
  Velocity の forwarding secret だけが防壁になる
- 状態確認: `ssh moripa@10.100.0.1 'echo "show stat" | sudo socat stdio /run/haproxy/admin.sock'`

## Linode 障害時の挙動

クラスタ内通信(etcd / API / kubelet / Pod の VXLAN)は拠点の LAN で直接
行うため、Linode が落ちても**クラスタ自体は動き続ける**。止まるのは
公開経路(Caddy / HAProxy)、ノードの egress(イメージ pull 等)、管理者の
wg 経由アクセスの 3 つ。ノード側は wg の keepalive で自動再接続する。

## control-plane(node1)障害時の挙動

各拠点の control-plane は node1 の 1台。node1 が落ちると API サーバーと
etcd が止まり、Cilium agent の API 接続も切れる(kube-proxy replacement
構成のため `k8sServiceHost` が VIP を直指定している)。ただし **node2 上の既存のデータプレーンはそのまま動き
続ける**(新規の Pod スケジューリングや設定変更ができなくなるだけ)。
復旧は node1 の wg / kubelet / etcd の状態確認から着手し、ディスク全損
なら etcd スナップショットからの復旧になる(バックアップの定期取得は未実装、
README の次のステップ参照)。

## ノードの wg が死んだとき

管理経路は wg のみ(`ansible_host` = wg アドレス)なので、ノードの wg が
落ちると Ansible からも SSH からも到達できなくなる(クラスタ内通信は LAN
直通なのでクラスタ自体は影響を受けない)。復旧手段:

1. 同一 LAN 内の別ノード経由で入る(`ssh moripa@10.100.0.12` →
   `ssh moripa@10.200.1.11`。`lan_address` は固定なので探す必要はない)
2. それも不可なら現地でコンソールログインし、node-bootstrap スクリプトを
   再実行(`make node-bootstrap HOST=...` で再生成して渡す)

ノードの DHCP アドレスは変わってもよい(どこにも焼き込んでいない)。
クラスタ用の `lan_address` は netplan で固定されており、DHCP とは無関係。

## wg syncconf と restart の使い分け

| 変更内容 | 反映方法 | 理由 |
|---|---|---|
| Peer の追加・削除、AllowedIPs の変更など | `wg syncconf`(Ansible の handler) | 既存セッション・クラスタ通信・公開経路の接続を切断せずに反映できる |
| `Address` / `MTU` / `PostUp` などの Interface 行 | `wg-quick@wg0 restart`(計画的に実施) | インターフェース自体の再構築が必要なため、フルトンネル確立後の restart は自分の管理セッションと公開経路を切断する(クラスタ内通信は LAN 直通なので無傷) |

## Nanode の転送量監視

Nanode は **1TB/月の転送量制限**と共有1vCPUという制約がある。フルトンネル
構成では4台分の外向き通信(イメージ pull、OS 更新、公開サービスのトラフィック)
に加え、Caddy / HAProxy の中継分がゲートウェイを経由するため(クラスタ内
通信は LAN 直通なので通らない)、Linode ダッシュボードで**月次**に転送量を
確認すること。

超過しそうな場合は、egress を直接出す split-tunnel(ノード側の `AllowedIPs`
を `10.100.0.0/24` に絞る)へ切り替えられる。公開経路は Caddy / HAProxy が
ハブ発で wg アドレスへ接続するため split-tunnel でも壊れない(ノードの外向き
IP が自宅回線になる点だけ変わる)。

## unattended-upgrades の blacklist 方針

`ansible/group_vars/all/main.yml` の `unattended_upgrades_blacklist` で
以下のパッケージを自動更新の対象から除外している。

```
kubeadm, kubelet, kubectl, kubernetes-cni, cri-tools, containerd
```

k8s とコンテナランタイムが夜間に無計画へ更新・再起動されるとクラスタが
壊れかねないため、これらは意図的に対象外にしてあり、更新は計画的に
手動で行う方針。
