## 目的

1. 4台のノードの**外向き通信を Linode の固定IPから出す**(自宅回線のIPを晒さない)
2. 外部からのアクセスを Linode で受けてノードへ届ける(サービス公開)。
   HTTP/HTTPS は **Caddy(L7 リバースプロキシ)**、HTTP 以外(将来の Minecraft など)は **HAProxy(L4)**
3. 管理用の踏み台経路(SSH over wg)を提供する
4. クラスタ通信(etcd / API / kubelet / Pod の VXLAN)は**運ばない**。拠点の
   LAN で直接通信させる(下記「第 2 サブネット」)

<Callout title="Cilium のノード間暗号化とは別物">
  これは Cilium のノード間 WireGuard 暗号化(`encryption.type=wireguard`)
  とは別物。あちらはクラスタ内 Pod 通信の暗号化で、このトンネルは南北
  (external)トラフィック用。混同しないこと(併用は可能)。
</Callout>

## トポロジ: hub-and-spoke

| ホスト | wg アドレス | 役割 |
|---|---|---|
| linode-gw | `10.100.0.1/24` | ハブ。ListenPort 51820。IP forward + masquerade + Caddy + HAProxy |
| site1-node1–2 | `10.100.0.11–12/32` | spoke。NAT 裏なので `PersistentKeepalive = 25` |
| site2-node1–2 | `10.100.0.21–22/32` | spoke。同上 |
| 管理者マシン | `10.100.0.100/32` | spoke(`wg_extra_peers`)。SSH / kubectl 用の管理経路 |

同一拠点のノード同士は wg 経由で通信**しない**(第 2 サブネットで LAN 直通)。
拠点間はクラスタレベルで接続しないため、拠点間トンネルも張らない。
ハブ側の `AllowedIPs` は各 peer の `/32` のみ(管理者マシン → ノードの
SSH / API のために wg0 → wg0 の forward は許可している)。

## 最重要の設計制約: k8s トラフィックをトンネルに乗せない

ノード側を安易に `AllowedIPs = 0.0.0.0/0` にすると、etcd・kubelet・Pod間
通信まで Nanode 経由になりクラスタが実用にならない。ただし
**wg-quick のフルトンネル機構はこれを自然に回避できる**。

- wg-quick は `0.0.0.0/0` 指定時、default route の差し替えではなく
  **fwmark + ポリシールーティング**(table 51820 + `suppress_prefixlength 0`
  ルール)を使う
- `suppress_prefixlength 0` により、**main テーブルにより具体的な経路が
  あればそちらが勝つ**。つまり:
  - クラスタ用サブネット内のノード間通信 → connected route
    (`<cluster_lan_cidr> dev <LAN NIC>`)が勝つ → 直接通信
  - Pod CIDR → Cilium が main テーブルに入れる経路、または VXLAN 外側パケットが
    ノードの `lan_address` 宛(= LAN 経路)になる → 直接通信
  - それ以外の外向き → table 51820 の default → wg0 経由

安全側に倒すため、spoke 設定には cluster_lan / Pod / Service CIDR の除外経路を
`PostUp` で明示的にも入れてある(冪等なので二重でも害はない)。

## 第 2 サブネット: LAN は DHCP のまま、クラスタ用アドレスを重ねる

拠点はアパートでルーターを触れず、LAN の IP を固定できる保証がない。
kubeadm は init/join 時点のアドレスを etcd・API サーバー証明書・kubelet の
InternalIP・Cilium の VXLAN 端点に焼き込むため、DHCP で変わり得る LAN IP は
使えない。そこで `roles/cluster_lan` が netplan で**ルーターと無関係な
サブネット(`cluster_lan_cidr` = `10.200.<site>.0/24`)の固定アドレス
(inventory の `lan_address`)を LAN NIC に追加**する。DHCP のアドレスは
そのまま残り、インターネット向け(wg のエンドポイント)に使われる。

| 項目 | 値 |
|---|---|
| kubelet `--node-ip` | `lan_address`(`roles/k8s_prereq` が `/etc/default/kubelet` で固定) |
| kubeadm `advertiseAddress` / `controlPlaneEndpoint` | `lan_address` / kube-vip の VIP(`kube_vip_address`、同じサブネット) |
| certSANs | VIP + 各 CP の `lan_address` + `wg_address`(管理者は VIP に届かないので wg アドレスで API に接続する) |
| Cilium `k8sServiceHost` / VXLAN の外側 | VIP / ノードの InternalIP = `lan_address` → LAN 直通 |

前提と注意:

- 2 台が**同じルーター/スイッチの有線ポート**につながっていること(同一 L2)。
  同じサブネットのアドレスを持つ 2 台は ARP で直接通信できるため、ルーターの
  設定も DHCP プールの範囲も関係ない
- 実際の LAN がたまたま `10.200.x.x` なら `cluster_lan_cidr` を変える
- LAN NIC の検出に `ansible_default_ipv4` は**使えない**。フルトンネル下では
  `ip route get` が policy routing で wg0 を返すため。`roles/cluster_lan/tasks/detect.yml`
  が main テーブルの default route(DHCP が入れる)から NIC を取る。NIC 名が
  確定したら group_vars の `lan_interface` で固定推奨
- `netplan apply` が systemd-networkd を再設定しても wg-quick のポリシールールを
  消さないよう、`ManageForeignRoutingPolicyRules=no` の drop-in を先に入れてある

## MTU

- `wg0` は **MTU 1360**。自宅回線が IPv4 over IPv6(MAP-E 等)や PPPoE で経路 MTU が
  1454〜1472 しかなく(管理機で実測 ≈1472)、1420 では ssh の鍵交換などが詰まる。
  ハブ・ノード・管理機のすべてで同じ値を使う(`wg_mtu`)
- クラスタ内(Cilium)の通信はトンネルを通らないため MTU は **1500**
  (`kubernetes/common/cilium/values.yaml` で明示し、wg0 の 1420 を誤検出させない)。
  Pod の MTU は VXLAN の 50 を引いて **1450**
- 南北の TCP はハブ側の MSS clamp で救済する

## wg 内の名前解決

ハブで dnsmasq(`roles/wg_dns`)を動かし、`<host>.wg.morino.party` を wg アドレス
に解決する(レコードは inventory から生成)。wg0 からの問い合わせにだけ応答し、
nftables も wg0 発の 53 番だけ通す。クライアントはそのゾーンだけをハブの DNS へ
向ける(Linux は `resolvectl domain wg0 ~wg.morino.party`、Windows は
`DNS = 10.100.0.1, wg.morino.party`)。一覧は `/docs/architecture/reference`。

## 公開経路は 2 種類: Caddy(L7)と HAProxy(L4)

| | Caddy(`gateway/caddy/Caddyfile`) | HAProxy(`tcp_routes`) |
|---|---|---|
| 対象 | HTTP/HTTPS(80/443) | L4 のサービス(Minecraft など。当面 `tcp_routes` は空) |
| 転送先 | ホスト名ごとに対象拠点の**全ノード** `:80`(Cilium の ingress controller、hostNetwork) | port ごとに対象拠点の**全ノード**の NodePort(`externalTrafficPolicy: Cluster`) |
| ノード障害 | passive ヘルスチェックで別ノードへ自動切替 | TCP ヘルスチェックで別ノードへ自動切替 |
| TLS | Caddy が終端(Let's Encrypt DNS-01 / Cloudflare でワイルドカード) | アプリ側 |
| クライアント実IP | `X-Forwarded-For`(Caddy が付け、Envoy がハブの `10.100.0.1` を末尾に追記する。アプリは先頭を読む) | 届かない。Minecraft なら前段の Velocity が modern forwarding で渡す |
| 認証 / 送信元制限 | `*.site<N>.private.dev.morino.party` は oauth2-proxy(GitHub org / MineAuth staff) | `allowed_sources`(nftables で送信元を絞る) |
| 両拠点 | 1 台の Caddy で site1 / site2 を混在可 | port ごとに拠点を指定 |

Caddy / HAProxy → ノードの通信はハブ自身(`10.100.0.1`)を送信元として wg0 へ
出るため NAT は不要で、ノード側は Cilium の `devices` に含まれる `wg0` で
受ける。Caddy は `*.site<N>.dev.morino.party` / `*.site<N>.private.dev.morino.party`
をワイルドカードで受けるので、この規約の名前なら Ingress を置くだけで公開される
(`/docs/architecture/multi-site`)。

ノードの `:80` は Envoy が hostNetwork で全 NIC に開くが、ノード側の nftables
(`roles/k8s_prereq` の `ingress-filter.service`、独立した table `inet moripa_ingress_filter`)
が **wg0 と lo 以外からの `:80` を drop** する。拠点 LAN の端末がノードの IP に `Host` ヘッダを
付けて直接送っても、oauth2-proxy を素通りして Headlamp などに触ることはできない。

## nftables 設定例(ハブ)

`ansible` の `wireguard` ロールが `proxy_public_ports` / `tcp_routes` 変数から生成する。

```txt
table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    udp dport 51820 accept          # WireGuard
    tcp dport { 80, 443 } accept    # Caddy(ハブ自身が listen)
    # tcp_routes の port ごとに accept が入る(allowed_sources 指定時は ip saddr で絞る)
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    tcp flags syn tcp option maxseg size set rt mtu   # wg(MTU 1360)向け MSS clamp
    ct state established,related accept
    iifname "wg0" oifname "eth0" accept   # spoke → internet(egress)
    iifname "wg0" oifname "wg0" accept    # 管理者 → ノード
  }
}
table inet nat {
  chain postrouting {
    type nat hook postrouting priority srcnat;
    oifname "eth0" ip saddr 10.100.0.0/24 masquerade   # egress のみ
  }
}
```

`sysctl net.ipv4.ip_forward=1` を忘れないこと。

## 鍵の管理と運用

- 秘密鍵は sops + age で暗号化して `ansible/host_vars/<host>/` に格納
  (`wg genkey` で生成、公開鍵は平文でよい)。鍵の一覧は
  `/docs/admin/keys` を参照
- spoke は NAT 裏のため keepalive 必須。ハブ再起動後も spoke 側から
  再接続される
- 設定変更の反映は **`wg syncconf`**(handler)で行い、`wg-quick@wg0
  restart` は使わない。restart は自分の管理セッションや Caddy / HAProxy 経由の
  既存接続を切断する(クラスタ内通信は LAN 直通なので影響しない)。
  `Address` / `MTU` / `PostUp` などの Interface 行を変えた場合のみ計画的に
  restart する
- Caddy のルーティング表(`gateway/caddy/Caddyfile`)は git push で反映される
  (ハブの `caddy-gitops.timer` が `caddy validate` を通してから
  `systemctl reload caddy`。wg には触れない)。Ansible 側の snippet 変更は `make gateway`
- 疎通確認は `wg show` の handshake、`ping 10.100.0.1`、
  `curl ifconfig.me` が Linode のIPを返すことで行う
- クラスタ健全性の確認として、同一拠点の他ノードの `lan_address` へ ping が
  通り、`ip route get` が wg0 を返さない(LAN 直通)ことをセットアップ後に
  必ず確認する(`roles/cluster_lan` が自動で検査する)
